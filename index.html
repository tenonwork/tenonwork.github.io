A five-component retail system

A client system for a Nairobi retail business, built between January and July 2026. I was the only developer, so the architecture, backend, security controls and all five applications are my work. The client’s branding has been removed from everything on this page.

  • Two mobile apps in React Native (Expo) with offline-first storage and sync.
  • Desktop point of sale in Electron and React.
  • Analytics dashboard in React with role-based access.
  • Shared backend on Supabase and PostgreSQL.

Decisions worth looking at

  • Logic lives in the database. The backend is built on more than 30 database functions behind row-level security.
  • Schema changes are additive and numbered. Migrations are written in sequence and add to the schema.
  • Batch submission is idempotent. The staff app can resubmit a batch without creating duplicates, which matters for an app that works offline.
  • Production migrations pass a gate. I wrote a security and performance gate that every production migration had to clear.
  • Development left a record. About 305 tasks were recorded through an AI-assisted dispatch workflow between 30 May and 11 July 2026.

Why it is built this way

  • Logic in the database. The rules live in one place, so there is a single source of truth. The apps mostly read and write, which means they run on any device however modest its processor and memory.
  • Offline-first. Internet and electricity are unreliable here, and a digitised system shouldn’t be at their mercy. Work continues without interruption and syncs when it can.
  • A gate before production. Development ran through an AI-assisted workflow, so the gate is an independent check on generated changes. It replaces guesswork with a pass or fail.

Problems I had to solve

  • Caching on slow, unreliable connections. The apps had to stay usable when the network was poor or absent.
  • Double submissions. Idempotency keys stop a retried submission from being recorded twice.
  • What to download, and when. I separated the data that is mandatory on install and login from the volatile data that can be discarded later.

What this shows: sole architectural ownership of a multi-application system. It does not show experience managing an engineering team.

local-ops: governing AI coding agents

A framework I started in September 2026 that lets AI coding agents work under review gates, staged releases and recorded approvals. Agents claim work from a queue, report results, then wait for a person to review them.

  • Stack: a local PostgreSQL store and a TypeScript MCP server.
  • Every write goes through database functions. Nothing writes to tables directly.
  • Production changes need a recorded approval.
  • Track record so far: 12 releases and 39 migrations, each rehearsed on staging.
  • Tests: separate suites for SQL, the MCP server and the scripts.
  • Source: github.com/tenonwork/local-ops-public (MIT). It is a sanitised public edition of the private deployment: history is a single curated commit and three migrations differ from the private ledger.

Why it is built this way

  • Controls are enforced in the database, not by instruction. An early failure showed why: a production-change task was claimed before its approval existed, and only a later step caught it. The fix lives in the database. Unapproved tasks are hidden from the agent and refused if claimed, without being used up.
  • An agent cannot approve its own work. Only the planning role can record a production approval. Otherwise the executing agent could approve itself and the gate would mean nothing.
  • Approval is bound to the exact file reviewed. It names the migration’s version and checksum, and promotion refuses if either has changed. A later failing record revokes an approval.
  • Evidence is fresh at apply time. Each promotion rebuilds the staging copy from a new production dump, which doubles as the pre-apply backup, and reruns the full test suite just before applying. An old passing run can’t be replayed.
  • Unused write paths are closed. Direct write permissions on every table are revoked from the planning role. All its tools already use database functions, so a partial revoke would have left open paths nobody was using.
  • One home for each rule. Rules live in versioned tables and the other documents point to them. Copies had drifted apart, so I removed them.
